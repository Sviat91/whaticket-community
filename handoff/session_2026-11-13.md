# Session: 2026-11-13

## Completed

Production incident: all inbound WhatsApp events stopped (whaileys provider, session 24). Outgoing sends
still delivered, ticket list showed `lastMessage` (written directly by `SendWhatsAppMessage`), but no
messages — incoming OR echoes of our own sends — reached the `Messages` table after ~10:39 local
(06:39 UTC). Restart and full rebuild did not help. Fixed and **confirmed working in production by the
user** (messages appeared).

Root cause (verified in `backend/node_modules/whaileys/lib`, v6.5.0):
- On connect whaileys calls `ev.buffer()` (`Socket/socket.js:553`) and only `ev.flush()`es when the
  server sends `<ib><offline/></ib>` (`Socket/messages-recv.js:730-735`). No timeout.
- Server sent `<ib><offline_preview count="N"/></ib>` (N grew 102 → 130 → 131 across restarts) and
  never sent the final `offline` node. whaileys has no handler for `offline_preview` (only a log at
  `socket.js:219`, emitted only when logger level is exactly `error`).
- Result: `messages.upsert`, `messages.update`, receipts etc. buffered forever.

Fixes, all in `backend/src/providers/WhatsApp/Implementations/whaileys.ts`:
1. Commit `752c529` — `wbot.ws.on("CB:ib,,offline_preview")` replies with
   `<ib><offline_batch count="100"/></ib>` (mirrors upstream Baileys). Plus the `messages.upsert` filter
   now accepts all `type === "append"` (offline-delivered incoming messages are `append`; previously
   dropped unless `fromMe`). Deployed alone — **insufficient** (still no flush).
   Plan/feedback: `handoff/offlineBatch_plan.md`, `handoff/offlineBatch_feedback.md`.
2. Commit `b1dd304` — safety net: 10s after `connection === "open"`, force `wbot.ev.flush()`. Flush is a
   no-op if already flushed. **This is what fixed it.**
3. Uncommitted (see In Progress) — guard `if (sessions.get(sessionId) !== wbot) return;` in that timer
   so a stale timer can't flush a dead socket after a reconnect within 10s (reviewer critical finding).
   Plan/feedback: `handoff/eventBufferFlush_plan.md`, `handoff/eventBufferFlush_feedback.md`.

## Decisions Made

- **Fix in code, not re-link the number.** Re-scanning QR would have cleared the server queue but
  lost the pending messages and wouldn't prevent recurrence.
- **Force-flush instead of reverse-engineering the offline protocol.** Library has no buffer timeout;
  a guarded 10s flush is robust regardless of how the server behaves. No data loss: flush releases
  events, it doesn't drop them; messages upsert by id, so no duplicates.
- **Do not edit `backend/.env` for log levels** — use `docker-compose.override.yaml` so no rebuild needed.
- Process note: the user wants diagnosis explained before any code change; do not launch coder until
  the user agrees to change code.

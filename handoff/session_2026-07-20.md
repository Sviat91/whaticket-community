**Part 2 — `nameLocked` feature (this session):**
The exact edge case flagged as an accepted risk in the prior summary recurred in production: WhatsApp force-disconnected the AVS session; user reconnected with a **new QR scan** (no data deleted, same number). Baileys' in-memory contact store (`wbot.store.contacts`) resets to empty on every reconnect/re-pairing, so before the async `PUSH_NAME` sync chunk repopulates it, incoming messages resolve to the contact's own self-declared WhatsApp name (`pushName`) instead of AVS's saved address-book name — and since `pushName` "looks like a real name," the `867ee13` heuristic let it silently overwrite the correct name.

Diagnosed live via code read (`whaileys.ts:685-700`, `CreateOrUpdateContactService.ts`), confirmed no proactive re-sync exists (`contacts.upsert`/`contacts.update` have no active listeners) — correction only happens reactively on that contact's next inbound message.

Decision: replace the heuristic entirely with a deterministic `nameLocked` boolean — once a human manually sets a contact's name via the UI, no automatic WhatsApp-driven path may ever change it again; before that, whatever comes in is written as-is (no more "does this look real" guessing).

Implemented via full orchestration flow (Mode: FULL — DB schema change):
- **Planner** → `handoff/nameLocked_plan.md` (7 steps, explicit merge-branch truth table for `nameLocked`/`name` when contacts merge by lid+number).
- **Coder** → migration (`20260720000000-add-nameLocked-to-contacts.ts`), `Contact.ts` model column, `CreateContactService.ts` + `ContactController.store` (manual create locks), `UpdateContactService.ts` (manual rename locks when name actually changes), `CreateOrUpdateContactService.ts` rewritten (all 3 branches + merge branch respect the lock; `isBareNumber`/`resolveName` deleted with zero remaining references). Two new Jest specs written under `backend/src/__tests__/unit/Contact/`.
- **Reviewer** → `handoff/nameLocked_feedback.md`, verdict APPROVED after line-by-line trace of all changed files and both (unexecuted) test specs.

## Decisions Made

- **`nameLocked` implemented (reversing the prior session's "declined for now")**: the heuristic-based protection (`867ee13`) turned out insufficient — it couldn't distinguish a contact's self-declared WhatsApp name from AVS's own address-book name or from a manually-corrected name, and this gap was hit for real after a forced reconnect. A deterministic lock, set only by explicit human action, replaces all content-based guessing.
- **Local `npm test` execution skipped for this feature**: running it needs a local MySQL (normally via Docker), and the coder agent's attempt to auto-start Docker Desktop for that triggered an unwanted system privilege prompt. User judged it not worth the detour, since this feature's real risk surface (WhatsApp session/reconnect timing) can't be exercised by a throwaway local test DB anyway — verification moved to the live server post-deploy instead. The two new Jest specs were still written and hand-traced against the service code by the reviewer, but never executed.
- **Feature commit kept code-only**: `handoff/*.md` planning/review docs were deliberately left out of the git commit, matching this repo's existing pattern of code-only feature commits.

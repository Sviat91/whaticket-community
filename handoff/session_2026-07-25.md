**Part 1 — Fixed broken WhatsApp replies (Mode: LIGHT, plan → coder → reviewer, APPROVED):**
Root cause confirmed by reading the installed `whaileys` (Baileys fork) library source directly (`backend/node_modules/whaileys/lib/Utils/messages.js`, `Socket/messages-send.js`): `whaileys.ts`'s `sendMessage`/`sendMedia` built a manual `contextInfo: { stanzaId, participant }` object and placed it as a sibling field inside the message content (e.g. `{ text: body, contextInfo }`) — but the library's `generateWAMessageContent` never reads a top-level `contextInfo` from content; it's silently dropped. The library's real mechanism is a `quoted: WAMessage` field passed via the **options** (3rd) argument of `sock.sendMessage(jid, content, options)`. Also found the existing `msgCacheLRU` has only a 10-minute TTL, too short to rely on for reconstructing quoted content (the repro itself quoted a 51-minute-old message), so the fix builds quoted content from the DB `Message.body` instead.

Fix (plan: `handoff/replyFix_plan.md`, review: `handoff/replyFix_feedback.md`, both APPROVED):
- `backend/src/providers/WhatsApp/types/ProviderOptions.ts` — added `quotedMessageBody?: string` to `SendMessageOptions`/`SendMediaOptions`.
- `backend/src/services/WbotServices/SendWhatsAppMessage.ts`, `SendWhatsAppMedia.ts` — thread `quotedMsg?.body` through as `quotedMessageBody`.
- `backend/src/providers/WhatsApp/Implementations/whaileys.ts` — `sendMessage`/`sendMedia` now build a `quoted = { key: { remoteJid, fromMe, id }, message: { conversation } }` object and pass it as the real Baileys `options.quoted`, removing the old dead `contextInfo` construction from all branches (including all 4 media types).
- New test: `backend/src/__tests__/unit/WhatsApp/WhaileysProviderReply.spec.ts`.
- `tsc` compiles clean; `npm test` not run locally (established preference, avoids MySQL/Docker).
- **User confirmed fixed in production** after deploy — replies now work.

**Part 2 — Auto-delete media files older than 30 days (Mode: LIGHT, plan → coder → reviewer, APPROVED):**
Confirmed via code read that all uploaded/downloaded WhatsApp media lands flat in `backend/public/` via one shared multer config, referenced only by `Message.mediaUrl` (nothing else writes into that folder — avatars/logos are external WhatsApp CDN URLs, not local files). No cron infra exists anywhere in the backend or Docker image (single `node dist/server.js` process) — asked the user whether to ship with a dry-run safety period first; user explicitly declined ("не буду заходить и проверять, нужно место на диске, пусть удаляет сразу, главное не сказывалось на работе системы"), so went straight to real deletion with batching for safety instead.

Fix (plan: `handoff/mediaCleanup_plan.md`, review: `handoff/mediaCleanup_feedback.md`, both APPROVED):
- New `backend/src/services/MessageServices/CleanupOldMediaService.ts` — finds `Message` rows with `mediaUrl != null` and `createdAt` older than 30 days (hardcoded, no env var — matches what was asked), batches of 200, unlinks the file (ENOENT silenced, other errors logged, never aborts the batch), unconditionally nulls `mediaUrl` in DB, 500ms pause between batches. Whole function wrapped in a top-level try/catch so it can never throw into its caller.
- `backend/src/server.ts` — calls it once on boot and schedules `setInterval(..., 24h)`; no new dependency (no node-cron), matching the existing `setInterval`-based pattern already used elsewhere in the codebase (`checkExternallyReadTickets`). Both `StartAllWhatsAppsSessions()` and `CleanupOldMediaService()` are fire-and-forget/unawaited, so the cleanup job cannot delay or block WhatsApp session restoration.
- New test: `backend/src/__tests__/unit/MessageServices/CleanupOldMediaService.spec.ts`.
- **User deployed and confirmed working**: production log showed `"CleanupOldMediaService: deleted 2162 media files"` ~40s after boot (user initially thought it hadn't run because they checked `docker compose logs` before the batched job finished — false alarm, explained and resolved in-session). No server-level cron needed or added; the job is fully self-contained in the Node process.

## Decisions Made

- **Priority order for the three reported issues**: replies (user-facing regression, zero session risk) → file retention (zero session risk, independent) → auto-healing (deferred — highest design uncertainty, and directly interacts with the still-being-verified `nameLocked` reconnect edge case, since more automatic restarts on the Baileys/AVS connection would mean hitting that untested window more often).
- **Reply fix**: build the Baileys `quoted` object from our own DB `Message.body` rather than relying on the library's 10-minute in-memory `msgCache` — chosen because the cache TTL is provably too short for realistic reply usage (confirmed by the bug repro itself), and the DB-backed approach is always available regardless of cache state. Deliberately did not add group-chat participant-resolution improvements or cache-based quoted-preview enrichment — out of scope, avoids scope creep on a bug fix.
- **Media cleanup: no dry-run, immediate real deletion** — reversing the initially-recommended dry-run-first approach after explicit user pushback: they will not manually review server logs to approve deletions, disk space is the actual constraint, and batching (200/batch, 500ms pause) was judged sufficient to satisfy the "must not affect system performance" requirement without a manual approval step.
- **Media cleanup: in-process `setInterval`, not a new dependency or OS-level cron** — the Docker image runs a single bare `node dist/server.js` process with no cron daemon; adding one (or a library like node-cron) was judged unnecessary complexity when the existing codebase already has precedent for `setInterval`-based periodic jobs (`checkExternallyReadTickets` in `wwebjs.ts`). This was also directly asked about by the user post-deploy and reconfirmed: no separate server-level cron is needed.
- **Both features implemented in Mode: LIGHT** (orchestrator wrote the plan directly after doing root-cause/design investigation personally, then coder implemented, then reviewer approved) — neither involved a DB schema change, new dependency, or architecturally ambiguous requirement, so FULL/planner-agent mode was not invoked.
- **Local `npm test` skipped for both features** (consistent with the 2026-07-20 session precedent) — verification done via `tsc` compile checks plus hand-traced/reviewer-verified Jest specs, with real confirmation coming from production logs/behavior after deploy rather than a local MySQL-backed test run.

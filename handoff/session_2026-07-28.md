# Session: 2026-07-28

## Completed

Root-caused and fully fixed the production bug (from `handoff/session_2026-07-27.md`) where outgoing
WhatsApp messages to some contacts silently never delivered (stuck at single grey checkmark forever),
regardless of contact. Confirmed fixed live in production by the user (Cargo 2 and Vasil tickets both
now deliver normally).

Three sequential fixes were shipped this session, each via the LIGHT/FULL coder+reviewer workflow:

1. **Deadlock retry in `StoreWppSessionKeys.ts`** (LIGHT mode) — added a bounded retry (3 attempts,
   200ms delay) for MySQL `ER_LOCK_DEADLOCK` errors when persisting Baileys signal/app-state-sync
   keys, so key writes aren't silently lost during reconnect windows. Real bug, but turned out not to
   be the cause of this session's main symptom. Plan: `handoff/wppKeyDeadlockRetry_plan.md`, feedback:
   `handoff/wppKeyDeadlockRetry_feedback.md`.

2. **`whaileys` npm dependency upgrade 6.4.14 → 6.5.0** (FULL mode) — found via `gh api
   repos/canove/whaileys/compare/...` that 6.4.16 shipped a fix ("add peer_recipient_pn on
   LID-addressed 1:1 sends") for a real but different LID-related bug. Confirmed zero dependency-tree
   changes between versions (low risk). Note: `backend/package-lock.json` is gitignored in this repo
   (long-standing 2020 convention) — this upgrade only applies via running `npm update whaileys`
   directly on the deploy host, not via git push/pull. Plan: `handoff/whaileysUpgrade_plan.md`,
   feedback: `handoff/whaileysUpgrade_feedback.md`. Real fix, but still insufficient for the main bug.

3. **tcToken LID/PN sibling-JID fallback in `GetWppSessionKeys.ts`** (LIGHT mode) — added a fallback
   lookup (swap `@s.whatsapp.net` ↔ `@lid` suffix, same digits) when a `contacts-tc-token` lookup
   misses. Real fix for a real mismatch, but still insufficient — production DB check on a second
   contact ("Vasil") showed the same `@lid`-only-token pattern, and the fix didn't resolve delivery.
   Plan: `handoff/tcTokenLidFallback_plan.md`, feedback: `handoff/tcTokenLidFallback_feedback.md`.

4. **The actual root cause and fix (FULL mode)** — WhatsApp's LID (anonymized ID) rollout: when a
   contact's message envelope carries no resolvable phone number, `convertToContactPayload` in
   `backend/src/providers/WhatsApp/Implementations/whaileys.ts` was fabricating a fake `Contact.number`
   from the LID's own digits (confirmed via DB: contact "Cargo 2" had `number = '268963787329585'` ==
   `lid = '268963787329585@lid'`). Every outbound send then addressed a nonexistent
   `<lid-digits>@s.whatsapp.net` account, silently rejected by WhatsApp
   (`"received 400 error in ack"`). Fixed by:
   - No longer fabricating `number` from LID digits (`whaileys.ts:677-680`).
   - Persisting empty numbers as SQL NULL, not `""` (avoids UNIQUE-index collisions across multiple
     LID-only contacts) — `CreateOrUpdateContactService.ts`, `UpdateContactService.ts`.
   - New `backend/src/helpers/BuildChatId.ts` helper addressing LID-only contacts via `@lid` instead
     of `@c.us`/`@s.whatsapp.net`, wired into `SendWhatsAppMessage.ts`, `SendWhatsAppMedia.ts`,
     `DeleteWhatsAppMessage.ts`, `SetTicketMessagesAsRead.ts`, `handleWhatsappEvents.ts`'s
     `handleQueueLogic`.
   - Added `"lid"` to `ShowTicketService.ts`'s contact `attributes` — the critical prerequisite;
     without it the whole fix would have been a silent no-op.
   - One-off idempotent data-repair migration
     (`backend/src/database/migrations/20260728000001-null-fabricated-lid-numbers.ts`) nulled out
     already-fabricated numbers for existing contacts at deploy time — contacts did **not** need to
     message again to become sendable; only the cosmetic display of their number waits for a future
     message that happens to carry a resolvable phone number.
   - `nameLocked` logic (from the 2026-07-25 session) was explicitly NOT touched anywhere — verified
     twice via `git diff | grep nameLocked`, per hard user constraint.
   - Plan: `handoff/lidContactNumberFix_plan.md`, feedback: `handoff/lidContactNumberFix_feedback.md`.
   - **Confirmed working in production by the user**: Cargo 2's number auto-populated with a real
     number after they messaged; Vasil was messaged successfully via `@lid` with `number` still NULL.

## Decisions Made

- **Root cause is the LID-fabricated-number bug, not session/token/deadlock issues.** The first three
  fixes shipped this session were all real, independently justified bugs, but none were the actual
  cause of the reported symptom — confirmed only after checking two different affected contacts
  against each fix and finding the pattern didn't fully resolve until the `Contact.number` fabrication
  was addressed at its source.
- **Do not switch `WHATSAPP_PROVIDER` back to `wwebjs`** (re-affirmed from 2026-07-27) — `wwebjs`
  never populates `Contact.lid` at all, so it can't hit this specific bug, but it also can't address
  LID-only contacts, and its own Puppeteer-freeze bug class remains unresolved upstream. Not a safer
  alternative.
- **`backend/package-lock.json` stays gitignored** — confirmed a deliberate, long-standing (2020)
  repo convention, not touched. Dependency version bumps in this repo must be applied directly on the
  deploy host (`npm update <pkg>`), not via git.
- **Data repair shipped as a migration, not a manual script** — the project's only automated deploy
  hook is `npx sequelize db:migrate` on container start; a migration guarantees the repair runs
  exactly once and can't be forgotten.

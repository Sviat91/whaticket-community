## Completed

Investigation only — no code changes this session. User reported a new production bug (via `superpowers:systematic-debugging`, Phase 1 root-cause investigation):

**Symptom reported:** for some contacts, outgoing WhatsApp messages stop being delivered after some time (an hour+), stuck showing a single grey checkmark in the custom frontend (`avschats.nodayoby.online`), while other contacts work fine. Self-heals only once the affected contact proactively sends a new message to us — the next outgoing reply then goes through. Not correlated with how long the contact had been offline. Two screenshots from the user (tickets #34 "Jurek", #88 "Mirza") illustrated the pattern.

**Investigation steps and findings:**
1. Confirmed via `Explore` agent that the frontend's ack-icon rendering (`frontend/src/components/MessagesList/index.js:610-623`) correctly reflects the DB `ack` field (0=clock,1=grey single,2=grey double,3/4=green double) — not a static icon, ruling out a frontend display bug.
2. Confirmed the app sets `ack=1` optimistically the moment Baileys echoes our own outgoing send (`convertToMessagePayload`, `whaileys.ts:496`), *before* any real WhatsApp server/device confirmation. `ack` only advances if a later `messages.update`/`message-receipt.update` event arrives for that message ID (`whaileys.ts:1152-1186`, `handleWhatsappEvents.ts:318-357`). **There is no timeout, retry, or logging anywhere in the app if that follow-up event never arrives** — a genuine silent delivery failure and a normal send look identical until/unless a later event shows up.
3. Ruled out the previous session's reply/quoted-message fix (`whaileys.ts` `sendMessage`/`sendMedia`) as the cause — read the current code in full, no error swallowing, no malformed `quoted` object construction possible, no retry/race constructs around the send call.
4. Found a secondary, independently-real bug (not the main issue, not yet fixed): `messages.update` handler (`whaileys.ts:1158`) casts Baileys' own `WebMessageInfo.Status` enum directly into the app's differently-numbered `MessageAck` enum with no translation — off by one, so the app's green "read" tick actually fires on delivery, not read.
5. User supplied today's `docker compose logs backend` output. Found the real evidence chain:
   - `2026-07-27 ~05:46`: WhatsApp force-disconnected the linked device — `stream:error` with `conflict type: device_removed` (session ID 24). Socket auto-reconnected (`Session connected`) within ~13s without a fresh QR scan being required.
   - Immediately after reconnecting, two `Error storing key in database` entries — MySQL `Deadlock found when trying to get lock` — while persisting Baileys `app-state-sync-key` records to the `WppKeys` table. `StoreWppSessionKeys.ts:40-47` catches and only logs this error; **it never retries, so the key data is permanently lost**.
   - For the following ~7 hours, the logs repeatedly show `"received 400 error in ack"` (Baileys' internal bad-ack/delivery-failure log, from `node_modules/whaileys/lib/Socket/messages-recv.js` `handleBadAck`) across many different contact JIDs — WhatsApp's own protocol reporting that messages did not reach the recipient device. The app has zero code listening for or reacting to this class of event at all.
   - Baileys does have a built-in auto-resend-on-bad-ack mechanism, but it: (a) only triggers for `attrs.error === "475"` specifically — our logs show `"400"`, a different code, so the existing mechanism would not fire even if enabled; (b) is disabled by default by the library's own authors because it caused WhatsApp account bans when looping in group chats. Confirmed this is not a "flip a flag" fix.
6. User then asked whether switching the WhatsApp provider back to `wwebjs` (used before the 2026-07-20 migration to `whaileys`, memory: [[project_wwebjs_puppeteer_freeze_incident]]) and dropping the `nameLocked` feature would be a clean way out. Researched and found:
   - `whatsapp-web.js` (wwebjs)'s Puppeteer freeze/hang class of bug is **not resolved** — long-standing recurring issues (GitHub #377, #1567) plus a new one as recent as January 2026 (#5758). Switching back would likely reintroduce the freeze risk, not eliminate a bug.
   - `nameLocked` is **not** whaileys-specific — it lives in the shared `CreateOrUpdateContactService`/`UpdateContactService` layer that both providers funnel through via `handleWhatsappEvents.ts`; `wwebjs.ts` also feeds `pushname` data through the same path (`wwebjs.ts:481-482`). Removing it when switching back would likely reintroduce the original manual-contact-rename-overwrite bug regardless of provider.
   - Recommended against switching providers; recommended a targeted fix instead (see Next Steps).

## Decisions Made

- **Do not switch `WHATSAPP_PROVIDER` back to `wwebjs`.** Both providers have known, unresolved bug classes (wwebjs: Puppeteer freeze/hang, recurring and unresolved upstream; whaileys: today's bad-ack/delivery-silent-failure). Switching trades one for the other, not a net improvement. Revisit only if the targeted whaileys fixes prove insufficient.
- **Keep `nameLocked` regardless of provider** — confirmed it protects a shared code path (`CreateOrUpdateContactService`) that both wwebjs and whaileys feed into, not a whaileys-specific quirk.
- **Root-caused, not yet fixed:** the message "stuck at single checkmark forever" bug is a real WhatsApp/Baileys-level delivery failure (`received 400 error in ack`), likely triggered/worsened by a `device_removed` stream conflict plus a silently-dropped MySQL deadlock on signal-key persistence right after reconnecting — not a frontend bug, not caused by the previous session's reply/quoted-message fix.
